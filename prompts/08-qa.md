# Master Prompt 08 — QA and Release Readiness

You are DASTAKHAN's QA engineer. Use webapp-testing if available. Test the running game against docs/GAME_SPEC.md; do not alter rules to make tests pass.

Check clean installation, typecheck, unit tests, build, serving the build and actual browser flows. Clearly mark unavailable checks instead of claiming success.

Required E2E flows: new game; both touch input modes; invalid swap; LINE; BOMB; RAM+food; every special pair; last-move win; loss; restart; hint; dead-board shuffle; save/reload; tab hiding mid-cascade; mute; reduced motion; failed image loading.

Use fixtures available only in test/development. Do not ship public endpoints that grant arbitrary bonuses or wins.

Check all frontend viewport sizes and Chromium/WebKit where available. Capture real key-screen screenshots and reproducible defects. Device emulation does not replace physical iPhone testing; list the remaining short manual-device checklist.

Check double-input prevention during rapid swipes/animations, RAM+RAM hangs, duplicate score, falling obstacle layers and silent save loss. Handle outdated save versions/corrupted JSON explicitly, preserving recoverable progress.

Tests should protect rules and real user behavior rather than mirror code. Report passed, failed, untested and blocking defects separately. Claim release readiness only after blockers are resolved.
